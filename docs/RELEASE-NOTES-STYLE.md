# 发布说明撰写规则

> 上游历史资料：本文继承自 HyperDuo，内容对应原项目当时的环境与实现。ColorDuo 面向 ColorOS 15–17（15/16 适配待实机验证）；当前说明见 [ColorDuo 文档索引](README.md) 和 [ColorOS 开发指南](COLOROS17-DEVELOPMENT.md)。

适用范围：`docs/release-notes/` 下的每一份发布说明，以及发布到 GitHub Release 的正文。

发布说明是给**用户**看的，不是给维护者看的。读者刚下载完新版本，只想知道两件事：这一版多了什么、修了什么。

---

## 一、结构

固定三节，顺序不变：

```
# 版本号

## 功能添加
- …

## 功能修复
- …

## 功能变更
- …

---

**安装**：覆盖安装即可，设置全部保留。
```

### 功能添加
用户能做的**新事情**。新增开关、新增可调项、新增可放置的组件。

### 功能修复
以前**坏掉或不对**的东西，现在好了。包括显示错位、设置不生效、预览与真机不一致。

### 功能变更
行为**改变了**，但不算新增也不算修复。移除开关、改默认值、合并两套重复的入口。

判断标准：

| 问 | 归属 |
| --- | --- |
| 以前做不到，现在能做到？ | 功能添加 |
| 以前做错了，现在对了？ | 功能修复 |
| 以前是这样，现在换个样？ | 功能变更 |

某节没有内容就整节省略，不写「无」。
---

## 二、每条怎么写

一行一条，格式：

```
- **干什么用的名字**：具体说明，说清在哪里找、怎么用、有什么边界。（#issue 号）
```

**标题加粗**，是用户能认出来的名字（也就是设置里显示的那个名字），不是代码里的概念。

冒号后面是**具体说明**，默认 40–70 字。要回答的是：

- 在哪里（「组件外观 → 电量数字」这样的完整路径，别让人去找）
- 打开后什么表现
- 有什么边界（只对某种样式生效、只影响新安装）

末尾括号里接 **issue 号**，没有就不写。issue 号是出处，不是主角 —— 放在句末，不放进标题、不做成表格。

### 例子

好：
```
- **充电时环内显示电量**：组件外观 → 电量数字，充电时中间显示百分比，拔线恢复原内容。仅环形样式。（#34）
```
这一条说清了名字、路径、表现、边界、出处。

不好：
```
- 新增充电时电量显示功能，通过修改 TrioAppearance.Ring 的仲裁逻辑实现
```
问题：说了实现没说什么用；没有设置路径；用户读不懂 `TrioAppearance.Ring`。

## 三、绝对不要写的

这几条是实际犯过的错误，不是假想。

### 1. 不写「未验证」「未在设备上确认」「只有单元测试」

发了版就是认定这些功能没问题。在发布说明里怀疑自己的功能，等于让用户不敢用他们刚下载的东西。

不确定就不该发。发了就不写。

### 2. 不写「未包含」

发布说明只说这一版**有什么**。没做的东西不属于这一版，写出来只会让人以为有内容被砍了。

工作排期是内部事务，不是产品说明的一部分。

### 3. 不写 issue 对照表

「Issue / 内容 / 是否已实现」这种表格是任务跟踪工具的做法。读者要的是「改了什么」，issue 号是句末的出处。

### 4. 不写代码标识符

`drawsBolt()`、`zoneAccepts`、`capReadingTrackWidth` 这些对用户是噪音。要描述**行为**，不是实现。

### 5. 不写内部取舍的来龙去脉

「我一开始想用 A，后来发现不行改用 B」属于 commit message，不属于发布说明。

---

## 四、写完自查

逐条过一遍：

1. 每一节的小标题是否都是**用户能认出来的名字**？
2. 每条是否都写了**设置路径**（如果它在设置里）？
3. 是否出现了代码标识符、类名、方法名？
4. 是否出现「未验证」「未包含」「暂无」「暂时不支持」？
5. 边界条件是否说清（只对某样式生效、只影响新安装）？
6. 有没有把同类改动拆成了七八条，其实可以合并成一条？

最后一条的取舍：一个开关一个条目，但如果同一个功能的几个滑杆，合成一条说明更好读。
